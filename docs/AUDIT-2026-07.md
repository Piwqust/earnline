# Earnline code audit — July 2026

Scope: the iOS app (`ios-app/`, ~24k lines Swift), the Supabase backend
(`supabase/migrations/`, `supabase/functions/`), and the build/CI setup. The web client
(`web/`) was read as a reference implementation for the sync protocol but was not audited
for its own defects.

Line references point at the code **as it was when the audit ran** (commit `950c42c`,
branch `main`). Items marked *Fixed* were addressed in the same change that added this
document; their line numbers will have moved.

The codebase is in good shape overall — defensively written, densely commented, with real
test coverage on the sync path. Most findings below are places where the implementation
drifted away from an invariant its own comments still describe.

## Correctness

### B1 — iOS deletes rows that were restored after their tombstone

**Critical. Causes silent local data loss and client/server divergence.**

`SyncCoordinator.applyRemoteTombstones` (`ios-app/earnline/Sync/SyncCoordinator.swift:556`)
decided purely on `shouldApplyRemote(localState:)` — *any* `.synced` local row named by *any*
remote tombstone was deleted, with no comparison between the tombstone's `deleted_at` and the
row's `lastSyncedAt`. Tombstones are replayed in full on every pass (`deletedAfter: nil`,
`SyncCoordinator.swift:89`) and are never pruned server-side, by design — see the comment at
`supabase/migrations/20260712090000_harden_web_sync.sql:2`.

The web client already implements the correct rule; iOS did not:

- `tombstoneApplies` compares `deletedAt >= (lastSyncedAt ?? syncUpdatedAt)` for a synced row
  (`web/src/sync/syncCoordinator.ts:138`).
- The pull side additionally drops remote rows that are not newer than the newest tombstone
  for that record (`web/src/sync/syncCoordinator.ts:280`).

**Reproduction.** Delete a line, wait ~1.5 s for the debounced sync to push the tombstone,
then tap Undo.

1. `SyncDeleteQueue.dequeue` finds no local tombstone — it was pushed and cleared already —
   so the restore leaves the remote tombstone in place.
2. The restored row is `.dirty` with `lastSyncedAt == nil`, so the next pass sees
   `conflictsWithDirtyLocal` return `true` and raises a spurious `SyncConflictError`.
3. After the user picks "Keep this iPhone's changes", the row is re-pushed and marked
   `.synced`, and the post-push pull sets `lastSyncedAt`.
4. On the *next* pass the row is `.synced`, `shouldApplyRemote` returns `true`, and the
   still-present remote tombstone deletes it locally — while the row remains in Postgres.
5. Once any later edit advances `syncCursor` past that row's `updated_at`, the inclusive
   `gte` cursor stops re-pulling it. The row is gone locally and orphaned remotely.

The same path affects a deleted-then-recreated client, and any peer device that pulls the
tombstone after the restore.

The doc comment on `UndoableDelete.restore` (`ios-app/earnline/Util/UndoDelete.swift:74`)
described exactly the guard that would have prevented this — "the tombstone-apply guard
(`deletedAt >= syncUpdatedAt` in `SyncCoordinator.applyRemoteTombstones`)" — but no such
guard existed in the coordinator. The comment documented the web implementation.

**Fix.** Ported both web rules into `SyncCoordinator`: a `tombstoneApplies` decision function
alongside the existing `shouldApplyRemote` / `conflictsWithDirtyLocal` pair, and a
newest-`deleted_at`-per-record map threaded into `pullRemoteRows` so a row covered by a live
tombstone stops flapping between deleted and re-inserted on every pass. `UndoDelete`'s comment
now describes what the code does.

**What this fix does *not* change.** Step 2 above — the spurious-looking conflict prompt on
the first pass after an undo that outran its push — still happens, and the web client behaves
the same way. It is the correct fail-closed outcome: the cloud says "deleted", this device
says "restored", and no clock comparison can decide that safely (`deleted_at` is a server
stamp, the local edit stamp is a device clock, and the codebase deliberately refuses to mix
them). The user is asked once; choosing this iPhone's copy now resolves it permanently
instead of losing the row two passes later. Making the prompt disappear would mean either
deleting the remote tombstone — the table is append-only precisely so peers that already
pulled it stay correct — or trusting a device clock. Both are worse than one prompt.

Regression tests: `oldTombstoneStillAppliesEvenAfterTheRowCursorAdvanced` still passes (a
tombstone newer than the row's baseline still deletes), plus `restoredRowSurvivesItsOwn­
RetainedTombstone`, `rowOlderThanItsTombstoneIsNotResurrectedByThePull`,
`skippedTombstonedRowStillAdvancesTheCursor`, and unit coverage of the decision rule itself.
The first of those was verified to *fail* against the old rule (`survivors.count → 0`) before
the fix was applied — the data loss is reproduced, not just theorised.

One existing test fixture had to change: `remoteClientTombstoneCascadesBeforePush` set
`lastSyncedAt: .now` as a don't-care value while its tombstone was dated in the past. That
combination cannot occur in reality — a row deleted remotely at 07-05 cannot also have been
observed alive at 07-25 — and it is exactly what the new comparison reads. The fixture now
uses a `lastSyncedAt` that predates the tombstone; what the test asserts is unchanged.

### B2 — Bulk deletes build an unbounded URL

**High.** `pushDeletes` (`SyncCoordinator.swift:141`) sent one DELETE per entity with every
tombstoned id in the query string. Reads are paged at 1000 via `fetchPaged`; deletes were not
chunked at all.

Deleting a client with hundreds of entries produces a URL past PostgREST's limit → HTTP 414 →
`lastSyncFailed`, the retry ladder fires, and every retry builds the identical oversized URL.
Sync stays wedged until the user resets local data.

The proxy edge function already rejects id lists longer than 1000 (`ids()`,
`supabase/functions/earnline-sync/index.ts:69`), so iOS could construct a batch the backend
would refuse outright. The web client has the same gap at
`web/src/sync/syncCoordinator.ts:211` — out of scope for this pass, but it should be fixed
the same way.

**Fix.** Two different bounds, because the two requests are constrained differently. The
tombstone upsert is chunked at `pageSize` (1000) to match the cap the proxy already
enforces on row batches. The DELETEs are chunked at 100, because their ids travel in the
URL at ~37 characters each and 1000 of them would still overflow the request line. Local
tombstones are cleared per chunk, so a failure partway through leaves the undelivered ones
queued for the next pass.

### B3 — Every sync pass pulls the full delta twice

**Medium.** `SyncCoordinator.sync` called `pullRemoteRows` twice with the *same*
`lastPulledAt` (`SyncCoordinator.swift:99` and `:116`). The second call exists only to read
the server-written `updated_at` for rows just pushed, but it re-fetched all five tables from
the original cursor, plus five `fetchCount`s and a full `Client` table fetch each time.

On a workspace with any real history this doubles network transfer, JSON decoding, and merge
work on every pass — and passes are frequent, because realtime echoes the device's own writes.

**Fix.** The second pull now starts from the first pull's observed maximum.

### B4 — `LineParser` strips a leading status word out of real task text

**Low.** `extractStatusWord` (`ios-app/earnline/Parsing/LineParser.swift:192`) matched
`lowered.hasPrefix(word + " ")` unconditionally. The doc comment two lines above names
`"Paid search ads audit"` as a line that must keep its words — but the code stripped `Paid`
and set the status to `.paid`.

The comment and the behavior disagreed. A leading status word on a line that carries no
amount and no `project: task` colon is far more likely to be task text than a status marker.

**Fix.** Implemented the comment's stated intent: a leading status *word* is only consumed
when the line also carries an amount or a colon. Trailing status words and leading emoji
markers are unchanged. If you prefer the old behavior, it is a one-line revert — see the
`requiresStructuralContext` guard.

### B5 — `syncNow` recurses instead of looping

**Medium.** `AppModel+Sync.swift:153` tail-called `await syncNow(context:)` to service
`followUpSyncRequested`. Realtime subscribes to the workspace with no self-origin suppression
(`AppModel+Sync.swift:465`), so the device's own pushes echo back as remote changes, which
call `queueSync`, which sets `followUpSyncRequested` when a pass is in flight. Each pass then
nests one frame deeper with no bound.

**Fix.** Converted to a bounded loop.

### B6 — Reset reports a stale realtime error as failure

**Low.** `resetLocalDataAndPull` (`AppModel+Sync.swift:191`) returned `syncError`, but
`startRealtime` also writes that field when a *subscription* fails (`:484`). A successful
reset could therefore surface "Realtime updates unavailable: …" as though the reset itself
had failed.

**Fix.** The reset now reports the error produced by its own pass.

## Performance

### P1 — The composer scans the whole Entry table on every keystroke

**High — this is the app's primary interaction path.**

`SmartComposer` declared `@Query(sort: \Entry.createdAt, order: .reverse) private var
allEntries: [Entry]` (`ios-app/earnline/Views/SmartComposer.swift:21`) — unbounded,
unfiltered, sorted, and live.

Its only consumer was `existingProjects` (`:185`), a computed property read from `body` via
`projectMenu`. Because amount, project, and task are all `@State` in the same view, every
character typed re-evaluated `body` and re-ran the distinct-name scan over the entire table.
The live `@Query` also re-fetched on every store change, including each of the three saves a
sync pass performs.

This directly undoes the ledger windowing work in `LedgerView`, whose whole point is that
launch never faults the full `Entry` table.

`commit()` (`:334`) additionally faulted every entry of the client just to compute
`sortIndex.min()`.

**Fix.** The unbounded `@Query` is gone. The distinct-project list is computed once in
`prime()` into `@State`, backed by a `FetchDescriptor<Entry>` with a `fetchLimit` and
`propertiesToFetch: [\.project]`. `commit()` uses a sorted descriptor limited to one row.

### P2 — Search re-scans the ledger several times per keystroke

**High.** `LedgerRowBuilder.searchHits` (`ios-app/earnline/Views/LedgerRowBuilder.swift:28`)
did `clients.flatMap { client.entries.filter … }` — a full relationship fault across every
client.

`rowBuilder` is a computed property on `LedgerView`, rebuilt on every body evaluation, and
`searchHits` was read at least three times per render (header hit count, `searchListContent`,
`ledgerRows`), with `searchEarnedTotal` reading it a fourth. So each keystroke in the search
field cost roughly four full-ledger scans.

`LedgerView` already builds a complete `searchSnapshot` when search opens
(`ios-app/earnline/Views/LedgerView.swift:278`) — the hit computation simply ignored it.

**Fix.** Hits are derived from the existing snapshot and cached in `@State`, keyed on the
query/token revision, so one scan serves the count, the row list, and the earned total.

### P3 — Pending list and heatmap day-tap fault everything

**Medium.** `Insights.pendingEntries` (`ios-app/earnline/Util/Insights.swift:402`) did
`clients.flatMap(\.entries)`; `dayContributions` (`:384`) iterated every client's entries on
every day tap in the heatmap.

Cheaper forms already existed in the codebase and were simply not used here:
`AppModel.refreshPendingReminders` (`ios-app/earnline/ViewModels/AppModel.swift:672`)
demonstrates the predicate-scoped `statusRaw == inProgress` fetch, and
`InsightsDashboardSnapshot.dailyEarnings` already holds per-day totals.

**Fix.** Both converted to scoped fetches.

### P4 — The ledger snapshot rebuilds on every save from any container

**Medium.** `LedgerView` subscribed to `ModelContext.didSave`
(`ios-app/earnline/Views/LedgerView.swift:451`) with no filter on the notifying context and no
coalescing.

One sync pass saves three times (`SyncCoordinator.swift:106`, `:122`, and
`AppModel+Sync.swift:128`), so each pass triggered three full re-aggregations — two fetches
and two counts apiece — and realtime triggers a pass per remote change. Because
`WorkspaceContainerHost` caches one `ModelContainer` per workspace and keeps them all alive
(`ios-app/earnline/earnlineApp.swift:38`), a save in a *different* container also refreshed
the visible ledger.

**Fix.** The subscription filters on the notifying context and coalesces bursts within a
runloop turn, so one sync pass triggers one re-aggregation.

### P5 — The tombstone table grows without bound (deferred)

**Medium — needs design, not a patch.**

Every sync pass on every client downloads the *complete* tombstone table, forever
(`SyncCoordinator.swift:89`). The migration comment at
`supabase/migrations/20260712090000_harden_web_sync.sql:2` correctly explains why naive
age-based pruning is unsafe: a device that has been offline indefinitely must still learn
about deletions it never saw.

A safe bound is possible but needs a mechanism the schema does not have yet: a per-device
sync watermark, so tombstones below the *oldest live device's* cursor can be pruned.
`earnline_workspace_members` and the paired-device registry already track devices, so the
watermark has a natural home — but revoking a device, or a device that never returns, has to
be handled explicitly or the watermark never advances.

Recommendation: design this alongside the R2 conformance work, and until then accept the
growth. For a personal ledger it is small; it is not a correctness problem.

## Backend

### S1 — A trigger function is callable by `anon` over the REST API

**Low practical impact, but it should not be in the API surface.**

Confirmed by Supabase's live security advisor against the production project
(`qpjfaapipwjultzvuxrm`): `earnline_entry_workspace_matches_client()` is `SECURITY DEFINER`
and reachable at `/rest/v1/rpc/earnline_entry_workspace_matches_client` by the `anon` role.

The cutover migration does revoke it from `PUBLIC`
(`supabase/migrations/20260714123553_authenticated_workspaces_cutover.sql:118`), but Supabase
sets default privileges that *also* grant `EXECUTE` on new functions in `public` to `anon` and
`authenticated` — and a `REVOKE … FROM PUBLIC` does not remove those role-specific grants.

Calling it is harmless in practice: plpgsql refuses to execute a trigger function outside a
trigger context. But the same default applies to every non-RPC function added to `public` in
future, so the pattern matters more than this instance.

**Fix.** A migration under `supabase/migrations/` explicitly revokes `EXECUTE` from `anon`,
`authenticated`, and `PUBLIC` for the trigger function. **It has not been applied** to either
project — applying it is an operator decision.

### S2 — `earnline-sync` batches are not transactional

**Low.** `action: "batch"` (`supabase/functions/earnline-sync/index.ts:258`) runs up to 12
actions sequentially against the caller-scoped client. A failure partway through leaves the
earlier actions applied and returns a single opaque 400.

This is survivable because the sync protocol is idempotent and retried, but it is a real
property of the transport and was not written down anywhere. Documented at the call site.

### S3 — Advisor findings that are correct by design

Recorded here so a future reader does not "fix" them:

- **`rls_enabled_no_policy`** on `earnline_pairing_tokens`, `earnline_workspaces`, and
  `earnline_workspace_members` (INFO ×3). This is intentional. The cutover migration revokes
  *all* privileges on these tables from `anon` and `authenticated`
  (`20260714123553_authenticated_workspaces_cutover.sql:37`), so they are reachable only
  through `SECURITY DEFINER` RPCs. Adding policies would widen access, not narrow it. A
  comment block now records this in the migrations.
- **`authenticated_security_definer_function_executable`** (WARN ×7) for
  `earnline_current_workspace`, `earnline_create_workspace`, `earnline_create_pairing_token`,
  `earnline_list_devices`, `earnline_revoke_device`, `earnline_disconnect_current_device`, and
  `earnline_has_workspace_access`. These *are* the intended authenticated RPC surface. Only
  the trigger function in S1 was a genuine finding.
- **`auth_leaked_password_protection`** (WARN). Does not apply — there are no user passwords
  in this system. Authentication is Sign in with Apple / OAuth, and device pairing uses a
  server-generated magic link against a synthetic address.
- **`unindexed_foreign_keys`** (INFO ×2) on `earnline_pairing_tokens`. Trivial and worth
  doing; covering indexes are included in the same migration as S1.

The rest of the RLS model reviewed clean. Workspace isolation goes through
`earnline_has_workspace_access(workspace_id)` on every table, and the
`earnline_entries_match_workspace` trigger correctly closes the gap a row-level predicate
cannot cover on its own — a guessed cross-workspace client UUID cannot become a foreign-key
relationship.

## Refactoring

### R1 — The `AppModel` aggregation forwarders were dead; `Insights` only partly so

**The initial read was too broad, and acting on it would have weakened the test suite.**

No *production* caller remained for any of the eleven forwarders in
`ios-app/earnline/ViewModels/AppModel.swift:623-660` — `entries(of:in:)`, `earnedEntries`,
`total(of:in:)`, `clientsWithEntries`, `monthTotal`, `monthlySeries`, `clientTotals`,
`topClients`, `monthlyDeltas`, `dailyEarnings`, `monthsWithData`, `monthPace`. That much held
up: `LedgerSnapshot` and `InsightsDashboardSnapshot` replaced them, and `monthPace`'s own doc
comment referred to "existing call sites" that no longer existed.

But the `Insights` methods behind them were not uniformly dead. `InsightsAggregationTests`
uses several as **differential oracles** — the simple, obviously-correct per-month
implementation is compared against the optimized single-pass snapshot:

```swift
#expect(snapshot.months        == ins.monthsWithData([a, b]))
#expect(snapshot.monthTotal(monthKey: nowKey) == ins.monthTotal([a, b], in: thisMonth))
#expect(snapshot.total(of: a, monthKey: nowKey) == ins.total(of: a, in: thisMonth))
```

That is real test value, and deleting it to satisfy a dead-code count would have been a net
loss. Splitting the two groups properly:

**Removed** — no caller at all, or covered only by tests that exercised them for their own
sake: the eleven `AppModel` forwarders, plus `Insights.clientsWithEntries`,
`earnedTotalsByMonth`, `monthlySeries`, `clientTotals`, `topClients`, `monthlyDeltas`,
`dailyEarnings`, and `monthPace`.

**Kept** — load-bearing as snapshot oracles: `entries(of:in:)`, `earnedEntries(of:in:)`,
`total(of:in:)`, `monthTotal(_:in:)`, `monthsWithData(_:)`, `isOverdue(_:)`. Tests now call
`app.insights.…` rather than the deleted forwarders.

**Moved rather than deleted** — the three `dailyEarnings` tests covered how a held amount is
spread evenly across its span and clipped to the visible window. That logic is still live, in
`InsightsDashboardInput.dashboardSnapshot`, and was only thinly covered there. The tests were
re-pointed at the dashboard instead of being dropped with the method they used to call.

Net effect: the misleading surface on the app's central observable object is gone, the
O(months × entries) production path is gone, and test coverage went up rather than down.

### R2 — The two sync engines have diverged (deferred)

iOS `SyncCoordinator` and web `syncCoordinator.ts` implement the same wire protocol with
materially different semantics:

| | iOS | Web |
|---|---|---|
| Tombstone vs. restored row | was unguarded (B1) | `deletedAt >= lastSyncedAt` |
| Pull-side tombstone filter | absent (B1) | present |
| Pass ordering | push deletes → pull → push rows | pull → push deletes → push rows |
| Conflict resolutions | `requireUserChoice`, `preferLocal` | + `preferRemote` |
| Delete chunking | none (B2) | none |

B1 has been closed, but the ordering difference and the missing `preferRemote` remain, and
there is no cross-client conformance test — nothing fails when the two drift.

Recommendation: write the decision rules down once (`docs/SYNC_RULES.md`) as a table of named
cases, then mirror those exact names as test cases in both `SyncCoordinatorTests.swift` and
`syncCoordinator.test.ts`. Do not attempt to share an implementation across Swift and
TypeScript; share the *specification* and the test names.

### R3 — `AppModel` is a god object (deferred)

746 lines, plus a 516-line sync extension and an 825-line auth extension, covering: currency
settings, appearance, app lock, undo staging, sync orchestration, retry/backoff, realtime,
connectivity monitoring, account state, and workspace/store identity.

The extensions keep each file readable, but they are all one type with shared mutable state
and no boundaries. The `Insights` extraction is proof the decomposition works; the natural
next splits are `AppLockController` (lock window, biometrics, cover/uncover),
`UndoCoordinator` (staging, expiry task, restore), and `WorkspaceIdentity` (environment,
workspace id, store mode, the `workspaceStoreIdentity` string).

Not scheduled — this is a refactor with real regression risk and no user-visible payoff, and
it should ride along with feature work in those areas rather than as its own change.

## Build & CI

- **C1 — No linter anywhere.** No `.swiftlint.yml`, no ESLint config, and no lint step in
  `.github/workflows/ci.yml`. Fixed: both configs added, tuned to the code as written rather
  than forcing a reformat, and wired into CI.

  security boundary for the web client and had no `deno check` or `deno test` job. Fixed.

  and UI jobs, with `.xcresult` uploaded on failure.
- **C4 — Stray file at the repo root.** An untracked file literally named `-`, containing a
  plist with a device UDID — the result of a mis-redirected `xcodebuild` invocation. Removed
  and added to `.gitignore`.

## What was verified, and what was not

Verified:

- **iOS unit suite**: 191 tests in 23 suites, green. Counts differ from before because dead
  code and its tautological tests were removed and new sync tests added.
- **iOS UI suite**: 24 tests, green.
- **The B1 data loss is reproduced, not inferred.** `restoredRowSurvivesItsOwnRetained­
  Tombstone` was run against the pre-fix rule and fails with `survivors.count → 0`.
- **P1 and P2 on a running app**, stress ledger loaded: the composer's project menu still
  populates from the new bounded fetch (7 distinct names), and search returns
  "780 results / $368 973" from the cached stats.
- **SwiftLint**: 0 errors, 52 warnings.
- **ESLint**: 0 errors, 19 warnings.
- **`deno check` and `deno lint`**: both clean on the two edge functions.
- **Web**: 88 tests green, build succeeds.

Not verified, and why:

- **End-to-end sync against Postgres.** The plan called for driving a delete/undo cycle on the
  simulator against the Test project. That is not reachable: `isSupabaseConfigured` requires
  the *production* environment plus a resolved account, and the Test environment is
  deliberately local-only. Doing it would mean signing into your account on the simulator,
  which needs your credentials. The mock-transport tests exercise the same
  `SyncCoordinator.sync` path end to end, including the real request and response shapes, but
  they are not a substitute for one live round trip — worth doing once by hand.
- **The new CI jobs have not run on GitHub Actions.** Each step was executed locally
  (SwiftLint, ESLint, `deno check`, `deno lint`, both `xcodebuild` invocations), so the
  commands and configs are known-good, but the workflow file itself gets its first real run on
  push.
- **The S1 migration has not been applied** to either Supabase project. Applying it is an
  operator decision; re-run the security advisor afterwards to confirm the finding clears.

One false alarm worth recording: the app appeared to crash on launch with
`-demoStressLedger` during verification. It was a stale binary — this machine has two
`DerivedData` directories for the project, and `find … | head -1` picked the older one. The
current build runs fine. If a crash with "Cannot use staged migration with an unknown model
version" ever shows up for real, it means a store file predates `EarnlineSchemaV3` and
`StoreRecoveryView` is the intended landing place.

## Not found

Worth recording, since absence of a finding is also a result:

- No force-unwraps or `try!` in production code paths (the one `as!` in
  `AuthBackdropVideo.swift:120` is the standard `layerClass` idiom and is safe).
- No `TODO` / `FIXME` / `HACK` markers anywhere in `ios-app/earnline`, `web/src`, or
  `supabase`.
- No hardcoded secrets. The preloaded Supabase values are publishable keys, and the workspace
  sentinels (`legacy-production-cache`, `local-test-cache`) are explicitly local-only.
- SwiftData model invalidation is handled consistently — `isInvalidated` / `isDeleted` gating
  appears at every site that survives a sync pull mid-render.
- The account/auth flow fails closed in the right places: `isOfflineTransportError` only
  admits concrete URL transport failures to the cached-membership path, so an HTTP 401/403
  can never be downgraded into offline access.
