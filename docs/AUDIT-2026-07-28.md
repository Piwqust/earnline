# Earnline — полный функциональный аудит iOS и backend

Дата отчёта: **2026-07-28**
Фактическое окно проверок: **2026-07-28 — 2026-07-29**
Проверенное состояние: `ee055147b3a2ac7bdebd6343612f851a9db232cc`, ветка `feat/period-recap`, вместе со всеми незакоммиченными изменениями.

## Вердикт

**NO-GO. Релиз текущего состояния блокируется.**

Основные причины:

1. Production REST schema cache не содержит `earnline_month_reviews` (`HTTP 404`, `PGRST205`), хотя iOS безусловно читает эту таблицу при каждом sync. Основной production sync-flow в текущей комбинации приложения и backend не подтверждён и, по наблюдаемому контракту, должен завершаться ошибкой.
2. Текущий guest→account importer открывает актуальное V3-хранилище схемой V2. Дефект воспроизведён: SwiftData возвращает `backwardMigration`, а `guestLedgerSummary()` скрывает ошибку и показывает пустой результат. `MonthReview` отдельно не входит ни в summary, ни в копирование.
3. iOS разрешает 48 project symbols, а SQL constraint и Edge Function — только 16. Выбор любого из 32 новых символов способен стабильно блокировать синхронизацию.
4. Полный UI-прогон на минимальном установленном runtime iOS 26.4.1 имеет 1 стабильный fail из 33.
5. SwiftLint завершается с exit code 2 из-за error-level нарушения, поэтому существующий CI lint gate не зелёный.
6. Нет подключённого staging и локального Supabase-окружения. Не выполнены обязательные независимые RLS, revoke, multi-device, 1001-row, partial-batch и backup/restore проверки. По заданному release-gate backend получает `NO-GO / BLOCKED`.
7. Backup-процедуры не включают `earnline_month_reviews`, а полноценное восстановление из созданного backup не реализовано и не доказано.

Этот аудит уменьшает неопределённость, но не может гарантировать отсутствие «всех возможных багов». Итог основан на выполненных тестах, статическом анализе и явно перечисленных пробелах.

## Границы аудита

Проверено:

- `ios-app/`: SwiftUI, SwiftData, auth, app lock, sync, CRUD, onboarding, parser/composer, settings, Insights, Pending, CSV-код, тесты и Release-конфигурация;
- SwiftData V1→V2→V3, guest/account store selection и guest→account import;
- Supabase migrations, Postgres constraints, grants/RLS по коду и безопасным production probes;
- Edge Functions `earnline-sync` и `earnline-pair-device`;
- backup/security scripts;
- зависимости Swift Package Manager;
- CI и Xcode/XcodeGen-конфигурация.

Исключено:

- весь `web/`, React, IndexedDB, browser E2E, hosting и web dependencies;
- цветовой contrast-аудит и визуальный редизайн;
- любые production CRUD, migrations, deploy, изменение Auth или удаление данных;
- исправления исходников в рамках этого аудита.

Production использовался только для отрицательных публичных запросов без записи. Staging не был подменён production.

### Короткие определения

- **Release gate** — обязательное условие, без которого сборку нельзя выпускать.
- **Staging** — отдельная тестовая копия backend, где разрешены записи и разрушительные сценарии.
- **RLS** — правила Postgres, ограничивающие строки доступным пользователю workspace.
- **Schema drift** — расхождение структуры базы с migrations в репозитории.
- **Tombstone** — запись об удалении, которую sync передаёт другим устройствам.
- **Cursor** — отметка последнего полученного изменения, с которой начинается следующий sync.

## Находки

### A-01 — Актуальное V3 guest-хранилище открывается importer-ом как V2

**Категория:** `REPRODUCED BUG`
**Severity:** P1
**Среда:** iPhone 17 simulator, iOS 27.0; временная копия проекта
**Data risk:** guest ledger становится недоступен для account import; `MonthReview` не переносится.

**Шаги воспроизведения**

1. Создать guest store с `EarnlineSchemaV3` и строкой `MonthReview`.
2. Открыть его через текущий `GuestLedgerMigration`.
3. Запросить summary или выполнить import в account store.

**Expected:** V3 store открывается через актуальную schema/migration plan; все поддерживаемые сущности попадают в summary и destination.

**Actual:**

- `guestContainer()` жёстко использует `EarnlineSchemaV2`;
- прямое открытие возвращает `SwiftDataError.backwardMigration` (`NSCocoaErrorDomain 134506`);
- `guestLedgerSummary()` скрывает ошибку через `try?` и возвращает пустой `Summary`, поэтому пользователю может вообще не показываться import;
- summary и copy path учитывают clients, entries, headings и project icons, но не `MonthReview`.

**Evidence:**

- `ios-app/earnline/earnlineApp.swift:375` — активный workspace использует V3;
- `ios-app/earnline/Util/GuestLedgerMigration.swift:45-46` — ошибка скрывается;
- `ios-app/earnline/Util/GuestLedgerMigration.swift:55-149` — перечисление копируемых типов;
- `ios-app/earnline/Util/GuestLedgerMigration.swift:167-172` — V2 hardcode;
- `guest-v3-import-audit.xcresult`: 0/2 с точными причинами.

Audit-тесты добавлялись только во временную копию и не меняют production source.

**Минимальная стратегия исправления:** открывать guest store схемой V3 с `EarnlineMigrationPlan`, добавить `MonthReview` в summary/copy, не скрывать migration error, затем закрепить V2 и V3 fixtures постоянными regression tests.

**Severity:** P1

**Минимальная стратегия исправления:** сначала применить migration в отдельном staging, проверить grants/RLS/REST schema reload и полный sync; затем отдельно согласовать backup и production migration. Не применять migration напрямую из этого аудита.

### A-06 — Финансовые и текстовые ограничения не совпадают между клиентом и Postgres

**Категория:** `STATIC RISK`
**Severity:** P1
**Среда:** SQL schema, Edge Function, iOS pull
**Data risk:** отрицательные/чрезмерные суммы и неограниченный текст могут попасть в общую базу и разойтись по устройствам.

iOS валидирует positive amount, максимальную сумму и длины полей. Базовая SQL-таблица использует `numeric(14,2)` и status enum, но не содержит:

- `CHECK (amount > 0)`;
- клиентского max amount;
- ограничений длины/формата для client name, color, currency, project, task и heading.

Edge sync проверяет IDs, project icons, month reviews и tombstones, но не воспроизводит полный клиентский contract для clients/entries/headings. iOS pull напрямую присваивает большую часть remote amount/text.

**Evidence:**

- `ios-app/earnline/Util/Validation.swift:3-10`;
- `supabase/migrations/20260629161744_create_earnline_sync_schema.sql:11-24`;
- `supabase/functions/earnline-sync/index.ts:98-136`;
- `ios-app/earnline/Sync/SyncCoordinator.swift:547-590`.

**Минимальная стратегия исправления:** закрепить инварианты в Postgres constraints/domains и повторить их в Edge validation; на pull применить fail-closed validation с диагностикой конкретной строки. Добавить SQL tests на boundary values.

### A-07 — Offset pagination может пропустить строку при конкурентном обновлении

**Категория:** `STATIC RISK`
**Severity:** P1
**Среда:** iOS sync и Edge `rows.list`
**Data risk:** строка может быть пропущена, а cursor затем продвинут дальше неё.

Оба пути сортируют изменяемый набор и читают его страницами через offset/range. Если уже прочитанная строка между page 1 и page 2 получает новый `updated_at`, она перемещается в конец. Непрочитанная строка сдвигается перед следующим offset и может быть пропущена.

**Evidence:**

- `ios-app/earnline/Sync/SyncCoordinator.swift:742-768`;
- `supabase/functions/earnline-sync/index.ts:188-204`.

**Минимальная стратегия исправления:** перейти на keyset pagination по `(updated_at, id)` с зафиксированной верхней границей snapshot; добавить concurrent-update test между страницами.

### A-08 — Обычные iOS upsert не разбиваются на chunks

**Категория:** `STATIC RISK`
**Severity:** P1
**Среда:** iOS sync
**Data risk:** большая dirty-очередь остаётся несинхронизированной и повторяет тот же неуспешный запрос.

Tombstones и delete IDs chunked, но dirty clients, headings, icons, month reviews и entries отправляются по одному неограниченному payload на тип.

**Evidence:** `ios-app/earnline/Sync/SyncCoordinator.swift:205-247`.

**Минимальная стратегия исправления:** chunk всех upsert с одинаковым документированным лимитом, помечать synced только успешно подтверждённые chunks, проверить 1001+ строк и потерю ответа в staging.

### A-09 — Device clock управляет временем tombstone

**Категория:** `STATIC RISK`
**Severity:** P1
**Среда:** SwiftData tombstone + Supabase sync
**Data risk:** устройство с будущими часами может сделать delete новее всех последующих restore/edit и повторно удалять данные.

`SyncTombstone.deletedAt` по умолчанию получает локальный `.now`; backend принимает это значение. Undo рассчитывает, что восстановленная строка станет новее tombstone. При clock skew в будущее это предположение нарушается.

**Evidence:**

- `ios-app/earnline/Models/SyncState.swift:379-395`;
- `ios-app/earnline/Sync/SyncCoordinator.swift:598-723`;
- `ios-app/earnline/Util/UndoDelete.swift:74-89`.

**Минимальная стратегия исправления:** назначать authoritative delete time на сервере или использовать server-issued monotonic revision; отдельно мигрировать/ограничить уже существующие future timestamps и покрыть skew тестами.

### A-12 — Security verifier может сообщить ложный «denied»

**Категория:** `STATIC RISK`
**Severity:** P2
**Среда:** `scripts/verify-supabase-security.mjs`
**Data risk:** broken/missing endpoint и RLS denial не различаются; security gate может быть ложно зелёным.

Verifier считает exposure только ответ `2xx` с непустым массивом. `401`, `403`, `404`, `5xx` и `200 []` объединяются в `denied/empty`. Он не делает write probes, cross-workspace checks, revoke и полный RPC/grant matrix.

**Evidence:** `scripts/verify-supabase-security.mjs:26-41`.

**Минимальная стратегия исправления:** задать ожидаемый status/error code для каждого probe, считать `404/5xx` инфраструктурной ошибкой, отдельно проверять read/write/foreign workspace/revoked JWT и запускать с временными staging identities.

### A-13 — Pairing не идемпотентен при потере успешного ответа

**Категория:** `STATIC RISK`
**Severity:** P2
**Среда:** `earnline-pair-device`
**Data risk:** pairing code потрачен, а клиент не получил session; создаётся ghost device identity до revoke/cleanup.

Function создаёт device user, redeem-ит token, создаёт session и только затем возвращает tokens. Если response теряется после commit, повтор того же request получает «invalid or expired». Client-visible idempotency key/recovery отсутствует. Cleanup в `catch` не запускается при успешно завершённой операции с потерянным сетевым ответом.

**Evidence:** `supabase/functions/earnline-pair-device/index.ts:69-128`.

**Минимальная стратегия исправления:** сделать redeem/session exchange идемпотентным по одноразовому request ID и разрешить безопасно получить тот же результат в коротком окне; добавить race/lost-response staging tests.

### A-14 — Edge batch не транзакционен и частично валидирует payload

**Категория:** `STATIC RISK`
**Severity:** P2
**Среда:** `earnline-sync` Edge Function
**Data risk:** клиент получает общий failure, но часть actions уже записана; retry может повторить другой набор side effects.

Код явно выполняет batch последовательно и не транзакционно. Для обычных clients/entries/headings нет полного field validation и общего ограничения размера body; лимит 1000 применяется на scoped row arrays, но не является end-to-end request cap.

**Evidence:**

- `supabase/functions/earnline-sync/index.ts:98-136`;
- `supabase/functions/earnline-sync/index.ts:258-273`.

**Минимальная стратегия исправления:** перенести atomic batch в Postgres RPC transaction либо вернуть per-action durable result/idempotency token; ввести schema validation и request byte limit до выполнения первой записи.

### A-15 — Ошибки Keychain storage могут скрываться при auth и logout

**Категория:** `STATIC RISK`
**Severity:** P2
**Среда:** supabase-swift 2.48.0 + iOS auth
**Data risk:** stale refresh token может остаться в Keychain после UI logout; PKCE storage failure выглядит как общий OAuth failure.

Используемая default storage реализация Supabase:

- хранит данные с `kSecAttrAccessibleAfterFirstUnlock`, не `ThisDeviceOnly`;
- catch-ит ошибки retrieve/store/delete и логирует их вместо передачи вызывающему коду;
- `signOut` публикует signed-out state после вызова storage remove, хотя реальная delete error могла быть скрыта.

Приложение отсоединяет account workspace и после auth signout error. На simulator нельзя доказать entitlement/accessibility поведение настоящего Keychain и biometric state.

**Минимальная стратегия исправления:** предоставить явный storage adapter с выбранным accessibility class, типизированными ошибками и проверяемым delete; не считать logout завершённым до подтверждённого удаления local credentials. Проверить на физическом устройстве.

### A-16 — Runtime warnings указывают на будущую auth-регрессию и UIKit hierarchy risk

**Категория:** `STATIC RISK`
**Severity:** P2
**Среда:** iOS 27.0 и 26.4.1 simulator
**Data risk:** expired local session после major SDK upgrade может быть ошибочно принята за начальную; unsupported toolbar hierarchy может сломаться на runtime update.

Стабильно наблюдались:

1. Supabase warning: initial session эмитится после попытки refresh; SDK предлагает `emitLocalSessionAsInitialSession: true` и явную проверку `session.isExpired`.
2. На iOS 26.4.1: `Adding 'UIKitToolbar' as a subview of UIHostingController.view is not supported and may result in a broken view hierarchy`.

Текущий код получает `auth.session`, поэтому немедленная expired-session ошибка не воспроизведена. Warning остаётся обязательным migration debt.

**Минимальная стратегия исправления:** зафиксировать требуемую initial-session semantics до обновления SDK, добавить expired/refresh-failure tests; найти источник UIKit toolbar injection и перенести его в поддерживаемую SwiftUI/UIKit hierarchy.
